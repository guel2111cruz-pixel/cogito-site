PREPARAR PRÓXIMO PARTICIPANTE // CICLO DA EXPERIÊNCIA

PERÍODO: Início de outubro de 2026
RELATO: Miguel (GL) e desenvolvimento do projeto

Implementamos na Área da Equipe o botão “Preparar próximo participante”. Depois de uma rodada confirmada, ele limpa a escolha local, apresenta novamente as quatro opções e fecha a área do operador, mantendo a autorização da sessão em memória.

Esse preparo não restaura a senha inicial da ESP32-CAM: o AP mantém a última senha aplicada até uma nova escolha. Encerrar a sessão é uma ação separada.

O ciclo organizado ficou: autorizar a equipe → participante escolhe → aplicar/verificar quando necessário → aguardar confirmação → demonstrar a conexão → preparar o próximo participante. Com a sessão já autorizada, a escolha inicia o envio automaticamente; se houver falha, verificamos a mesma rodada.

PERÍODO: Início de outubro de 2026
RELATO: Miguel (GL) e desenvolvimento do projeto

Integramos o controle USB/serial à ESP32-CAM para trocar a senha do AP SILENT_BREACH entre as quatro opções fictícias do App: 12345678, password, qwerty12 e cogito26.

No teste físico relatado por Miguel, um segundo dispositivo conseguiu conectar ao AP usando password, a senha escolhida. Isso validou a associação externa naquela rodada, além da confirmação serial. Não estendemos esse resultado às demais opções sem um registro equivalente.

Desenvolvemos uma ponte em Python executada no notebook/PLOT. O tablet comunica-se com ela por HTTPS na rede da equipe; a ponte encaminha a escolha à ESP32-CAM por USB/serial, a 115200 baud.

[LOG_015]

TESTE COM NMAP // DESCOBERTA DE HOSTS E ABERTURA DE UM SERVIÇO HTTP

PERÍODO: 01/10/2026
RELATO: Miguel (GL)
AMBIENTE: Rede 10.0.0.0/24, A15 com Termux e PLOT

Iniciamos com nmap -sn 10.0.0.0/24. O resultado mostrou vários hosts ativos, indicados como up. Entre eles estava 10.0.0.56, endereço do meu celular A15. A opção -sn realiza descoberta de hosts sem a etapa de varredura de portas.

Em seguida, utilizamos nmap -sV 10.0.0.56. Conforme observado no teste, todas as portas verificadas estavam fechadas naquele momento, antes de iniciar o servidor HTTP. Esse comando verifica, por padrão, as 1.000 portas TCP mais comuns; o resultado não descreve todas as portas possíveis do aparelho.

No A15, pelo Termux, executamos python -m http.server 8080. O comando iniciou um servidor HTTP na porta 8080 do celular, disponibilizando o diretório em que foi executado.

Com o servidor em execução, utilizamos no PLOT nmap -sV -p 8080 10.0.0.56. Dessa vez, o Nmap indicou a porta 8080/tcp como open, conforme o relato do teste.

A comparação mostrou a diferença entre uma porta fechada, sem aplicação escutando, e uma porta aberta, com um serviço aceitando conexões. A opção -sV tenta identificar o serviço e sua versão; o nome e a versão exibidos na saída não foram informados.

O teste demonstrou a abertura de uma porta ao iniciar um serviço. Uma porta aberta, por si só, não comprova uma vulnerabilidade.

RESULTADO: Hosts ativos descobertos, portas verificadas inicialmente fechadas e porta 8080 aberta após iniciar o servidor HTTP, conforme relato de Miguel (GL). As saídas completas do Nmap ainda não foram incluídas no acervo.

REFERÊNCIAS TÉCNICAS: Nmap — descoberta de hosts ↗ · Estados das portas ↗ · Detecção de serviços ↗ · Portas verificadas ↗ · Python — servidor HTTP ↗

02 // APP SCCT / PWA

Arquivos

feira/index.html, feira/app.js, feira/app.css, feira/sw.js, feira/manifest.webmanifest e ícones locais.

Funcionamento

As quatro opções são 12345678, password, qwerty12 e cogito26. O toque cria um UUID e um índice de escolha (0–3); a rodada fica em scct-pending no localStorage. O App esconde as opções e aguarda confirmação. Se a sessão já estiver autorizada, tenta aplicar automaticamente.

A Área da Equipe autoriza pela rota GET /api/health. O código de autorização permanece em memória, sem persistência no localStorage. A verificação de saúde confirma a bridge, sem verificar o hardware. A aplicação usa POST /api/select com id e choice.

O service worker guarda o shell da interface em scct-shell-v1. Offline exige carregamento prévio em HTTPS confiável ou localhost. Guardar uma escolha offline não aplica a senha na placa; após reconectar, a equipe verifica a mesma rodada.

Próximo participante

O botão só permite avançar quando não existe escolha ou quando seu estado é applied. Limpa a rodada local e fecha a área do operador. A autorização é mantida; a senha do AP não é restaurada. “Encerrar sessão” remove a autorização em memória.

feira/app.js // aplicação e confirmação
async function apply() {
  if (!pending || !credential || busy || pending.state === 'applied') return;
  busy = true; render(); message('Aguardando aplicação e confirmação da placa…');
  try {
    const result = await api('/api/select', {id:pending.id, choice:pending.choice});
    if (result.id !== pending.id || result.state !== 'applied') throw new Error('Resposta sem confirmação de aplicação.');
    pending.state = 'applied'; save(); message('Placa confirmou: senha aplicada. Clientes do AP precisam reconectar.');
  } catch (e) { message(`${e.message} Estado incerto: reconecte e toque em aplicar/verificar para consultar a mesma escolha.`); }
  finally { busy = false; render(); }
}
feira/app.js // preparar próximo participante
function clear() { pending = null; save(); render(); message('Aguardando escolha.'); }
$('next').addEventListener('click', () => { if (!pending || pending.state === 'applied') { clear(); $('operator').open = false; } });

A cadeia tablet → placa → segundo aparelho foi relatada como bem-sucedida com password. O teste de reabertura offline e a execução repetida do botão de próximo participante não possuem resultado específico documentado no relato disponível.

03 // BRIDGE PYTHON / SQLITE / HTTPS / SERIAL

Arquivos e dependências

control/bridge.py, control/requirements.txt e control/test_bridge.py. Usa SQLite, ssl e servidor HTTP da biblioteca padrão, com pyserial para a porta USB.

Funcionamento

Valida UUID, índice 0–3 e formato do pedido. Confere Host, Origin e autorização Bearer. O banco jobs mantém id, choice e state; registra uncertain antes de tocar o hardware. Uma rodada já aplicada retorna seu resultado; uma rodada incerta impede uma nova solicitação com outro identificador.

A serial transmite SET <id> <choice> <chave omitida> seguido de nova linha. A bridge espera até 12 segundos por APPLIED <id>. Sem confirmação, a aplicação permanece incerta. A resposta aplicada é o registro daquela rodada, não uma leitura contínua do estado atual da placa.

Comandos relevantes

Exemplos adaptados do guia do projeto. Substitua a porta, o IP e os caminhos pelos valores locais; configure SCCT_TOKEN e SCCT_DEVICE_KEY fora do HTML com valores distintos. Nenhum segredo está incluído.

python -m pip install -r control/requirements.txt
python control/bridge.py --port COM5 --cert scct-cert.pem --key scct-key.pem --origin https://192.168.1.20:8443 --db scct-jobs.sqlite3
# No Linux: substituir COM5 por /dev/ttyUSB0
# Tablet: https://192.168.1.20:8443/feira/

Porta COM5 e IP acima são exemplos do guia, não valores confirmados do teste. O certificado precisa ser confiável no tablet e corresponder ao endereço utilizado. A ponte serve apenas os arquivos públicos da PWA; banco, firmware e segredos ficam fora dessas rotas.

control/bridge.py // confirmar e persistir APPLIED
if line == f"APPLIED {data['id']}":
                        conn.execute("UPDATE jobs SET state='applied' WHERE id=?", (data['id'],))
                        conn.commit()
                        return {'id':data['id'], 'state':'applied'}

Funcionamento integrado confirmado pelo relato da troca real e associação externa. Há testes automatizados em control/test_bridge.py; a presença do arquivo não é apresentada como resultado de execução nesta entrega. 04 // FIRMWARE AI THINKER ESP32-CAM

Arquivo

control/firmware/scct_control/scct_control.ino. Componentes: esp_camera, WiFi, WebServer, Preferences e sockets lwIP.

Funcionamento

Integra a câmera e o streaming MJPEG ao controle serial autenticado. A página local atende em / e o stream em /stream. O controle de senha chega pela USB/UART, sem rota HTTP de controle no AP.

O comando valida identificador, chave e índice de escolha; reinicia o AP com a senha selecionada e grava ap-record em Preferences. Só envia APPLIED depois de configurar o AP e persistir o registro. Repetir a última rodada com o mesmo índice permite confirmar sem criar uma escolha distinta.

No código de referência, o SSID é SILENT_BREACH e a senha inicial, sem registro anterior, é admin123. Depois disso, a placa restaura a última escolha persistida. O botão de próximo participante no tablet não altera esse estado.

scct_control.ino // troca do AP e confirmação
apGeneration++;
  WiFi.softAPdisconnect(true); // All demo AP clients disconnect here.
  delay(250);
  WiFi.mode(WIFI_AP);
  apReady = WiFi.softAP(SSID, PASSWORDS[selected]);
  if (!apReady) { Serial.println("ERROR " + id + " AP"); return; }
  // One durable record keeps id and password choice consistent across power loss.
  String record = id + " " + String(selected);
  if (prefs.putString("ap-record", record) == 0) { Serial.println("ERROR " + id + " STORAGE"); return; }
  lastID = id;
  activeChoice = selected;
  Serial.println("APPLIED " + id); // Sent only after softAP succeeds and record persists.
